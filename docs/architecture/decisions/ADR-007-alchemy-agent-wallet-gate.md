# ADR-007 — Alchemy Agent Wallet capability verification is a hard gate

- **Status:** Open (verification pending) · 2026-11-05 · **updated 2026-11-05 (RPC read path verified; Agent Wallet gate unchanged)**
- **Context:** Stage 12 requires confirmation that Alchemy's Agent Wallet / Wallet API supports: session capabilities, Solana transaction formats, **custom-program instruction compatibility**, signing behaviour, session restrictions/expiry/revocation, sponsorship and network coverage. The approved application id is `q15y93g86sfgd0rb`.
- **Update 2026-11-05:** A Solana RPC API key for the approved app is now configured. `scripts/alchemy-probe.ts` verified the RPC **read** path live against solana-devnet (getHealth, getSlot, token-account reads, signature-status parsing). This does **not** touch the Agent Wallet gate: an RPC key is not Wallet API credentials, so `agentWalletSigning` remains **UNVERIFIED**. Cluster correction: Alchemy serves Solana mainnet-beta + devnet only; staging now targets solana-devnet (the configured USDC mint is Circle's devnet USDC).
- **Decision:** The application treats Agent Wallet signing as **UNVERIFIED**. The chain adapter exposes capability probing and health checks that report `verified: false` until a configured endpoint answers. The product must not claim Agent Wallet-backed signing until this check passes in staging. If custom Solana program instructions are unsupported, the documented fallback is: buyer-org treasury signing for escrow operations with agent-side actions limited to platform calls (mandate-bounded), which preserves the directive rule "do not give agents unrestricted signer access".
- **Consequences:** No marketing or UI copy may assert Agent Wallet support; staging results carry `LEDGER-ONLY`/`DEMO` references and must never be presented as onchain confirmations. Clearing this gate requires Agent Wallet credentials (separate from the RPC key) and a dedicated probe; the RPC key must also be rotated since it transited an untrusted channel.
